# Comments from atproto

[![CI](https://github.com/arinspunk/atproto-comments-plugin/actions/workflows/ci.yml/badge.svg?branch=main)](https://github.com/arinspunk/atproto-comments-plugin/actions/workflows/ci.yml)

![Comments from atproto: the replies to an AT Protocol post shown as the comments of a WordPress post](.github/assets/readme-banner.png)

WordPress plugin that shows the replies to an AT Protocol post — from Bluesky or any compatible app (Mu, Deer, etc.), on any server (Eurosky, a personal one, etc.) — as the comments of a WordPress post. Publish the post from the editor, or paste the link to an existing one, and the conversation appears under your entry, threaded, in your site's language. Visitors reply from their own app; there is nothing to moderate in WordPress.

- **Using the plugin:** see [`readme.txt`](readme.txt) for features, installation, FAQ, external services and privacy. <!-- When published: and the plugin page on WordPress.org. -->
- **Working on the plugin:** read on.

Comments from atproto is an independent project by the author of the [`atproto-comments`](https://github.com/arinspunk/atproto-comments) web component. It is not affiliated with or endorsed by AT Protocol or Bluesky.

## How it works

- **The visitor's browser renders the thread.** The server only prints an `<atproto-comments>` element with the post's `at://` URI; the bundled web component loads the replies from the configured AppView (by default `https://public.api.bsky.app`). The server never proxies or stores comments.
- **The server stores three things:** the link of each entry (post meta `_atproto_thread_uri`), the display settings (`atproto_comments_settings`) and the site's AT Protocol account (`atproto_comments_account`, with the app password encrypted).
- **Publishing and deleting the anchor post** are editor actions, through the plugin's REST routes. The server resolves the account's identity (handle → DID → PDS, no hard-coded server), opens a session on its PDS and creates or deletes the post, all within a 25-second budget. Only Editors and Administrators can publish or delete by default (`atproto_comments_publish_capability` filter).
- **Linking by hand** needs no account: paste an `at://` URI or a post URL from any compatible app; a handle in the URL is resolved to its DID on the server.

The design decisions behind each part, with the alternatives that were discarded, are in [`openspec/changes/archive/`](openspec/changes/archive/).

| `includes/class-identity.php`, `class-xrpc.php`, `class-crypto.php`, `class-deadline.php` | Identity resolution, XRPC client, app password encryption, time budget |
| `src/editor/` | Block editor panel (link field, publish form, linked state) |
| `src/settings/` | Connection test button on the settings page |
| `templates/comments.php` | Replacement for the theme's comments template |
| `scripts/vendor.mjs` | Copies the web component from `node_modules` to `assets/vendor/` |
| `tests/php/`, `tests/js/` | PHPUnit (WordPress test suite) and Vitest tests |
| `tests/fixtures/thread-uris.json` | Link normalization cases shared by the PHP and JS tests |

| `.claude/` | Skills and commands for Claude Code: OpenSpec workflow, `flujo-pr`, `wp-env` |

`build/` and `assets/vendor/` are generated by `npm run build` and are not versioned.

## Development

Requirements: Node 22 (version in `.nvmrc`; with nvm, `nvm use`) and Docker (for `wp-env`). PHP and Composer run inside the containers.

```bash
npm ci
npm run build            # copies the component to assets/vendor/ and builds the editor panel and the settings script
npx wp-env start         # http://localhost:8888 (admin / password)
npx wp-env run tests-cli --env-cwd=wp-content/plugins/atproto-comments composer install
```

### WordPress and PHP combinations

`.wp-env.json` sets the minimum combination: **WordPress 6.5 and PHP 7.4**.

For the current combination (**latest WordPress and PHP 8.3**), create a `.wp-env.override.json` (not versioned):

```json
{ "core": null, "phpVersion": "8.3" }
```

or, without touching files, change only PHP with an environment variable:

```bash
WP_ENV_PHP_VERSION=8.3 npx wp-env start --update
```

After switching combinations, run `npx wp-env start --update`. To go back to the minimum, delete the override and run the command again.

### Quality

```bash
npm run lint:js
npm run test:js                   # Vitest, in Node
npx wp-env run cli --env-cwd=wp-content/plugins/atproto-comments composer phpcs
npm run test:php                  # PHPUnit (WordPress test suite in wp-env)
npm run test:php:multisite        # the same suite as multisite
npm run plugin-check              # exits 0 even with errors: check the output
```

## Working with OpenSpec

Behavior is specified before it is built, with [OpenSpec](https://github.com/Fission-AI/OpenSpec):

- **`openspec/specs/`** is the source of truth: what the plugin does today, one folder per capability (`comments-display`, `thread-linking`, `plugin-settings`, `atproto-account`, `anchor-post-publishing`), as requirements with scenarios.
- **`openspec/changes/<name>/`** holds each change in progress: `proposal.md` (why and what), `design.md` (how, with discarded alternatives and what is checked on WP 6.5 and on the latest version), `specs/` (deltas: requirements added or modified) and `tasks.md` (steps, each ending with how it is verified). Tooling-only changes have no specs and set `skip_specs: true` in `.openspec.yaml`.
- **`openspec/changes/archive/`** keeps finished changes. Archiving a change merges its deltas into `openspec/specs/`.
- **`openspec/config.yaml`** has the project constraints every change must respect (minimum versions, prefixes, no CDN, external services).

The usual cycle, with Claude Code (commands in `.claude/commands/opsx/`) or the `openspec` CLI:

1. Propose: `/opsx:propose` (or `/opsx:new`), then review and adjust the artifacts.
2. Validate: `npx @fission-ai/openspec validate <name> --strict`.
3. Implement on a branch named after the change: `/opsx:apply <name>`.
4. Archive on the same branch, before merging: `/opsx:archive <name>`.

Artifacts are written in Spanish (`openspec/config.yaml`); code, comments, `readme.txt` and this README are in English.

## Contributing

- **Small fixes** (typos, an obvious bug): open a pull request directly.
- **New behavior or a change to existing behavior:** open an issue first, or a pull request with only the OpenSpec change (`proposal.md` at least), so the approach can be agreed on before writing code.
- **Branches and pull requests:** one branch per change, named after it; everything reaches `main` through a pull request with green CI (see [Workflow](#workflow)). Pull requests are squash-merged.
- **Commit messages:** [Conventional Commits](https://www.conventionalcommits.org/) in English, `<type>(<scope>): <summary>` (for example `fix(display): skip password-protected posts`).
- **Code:** WordPress Coding Standards (`composer phpcs`), PHP 7.4 syntax, the prefixes in `openspec/config.yaml`, and tests in the same change as the code they cover.

## Security

Please don't report vulnerabilities in public issues. Use GitHub's [private vulnerability reporting](https://github.com/arinspunk/atproto-comments-plugin/security/advisories/new) instead. You'll get an answer as soon as possible, and the fix will be published together with an advisory.

## CI

`.github/workflows/ci.yml` runs on every push to `main`, on every pull request against `main`, and manually from the Actions tab. It has four checks, which run in parallel:

| Check | What it does | How to reproduce it locally |
|---|---|---|
| `js` | `npm ci`, `npm run lint:js`, `npm run test:js`, `npm run build` | The same commands |
| `phpcs` | `composer install` and `composer phpcs` with PHP 7.4 on the runner | `npx wp-env run cli --env-cwd=wp-content/plugins/atproto-comments composer phpcs` |
| `phpunit (minimum)` | WordPress 6.5 + PHP 7.4: `npm run test:php` and `npm run test:php:multisite` | Without `.wp-env.override.json`: `npx wp-env start --update` and both commands |
| `phpunit (latest)` | Latest WordPress + PHP 8.3: the same, plus `npm run plugin-check` (fails on any `ERROR`) | With the current-combination override: `npx wp-env start --update`, both commands and `npm run plugin-check` |

Actions are pinned by SHA; Dependabot (`.github/dependabot.yml`) proposes their updates every week.

## Workflow

`main` is protected by the ruleset versioned in `.github/rulesets/main.json`:

- Every change goes in through a **pull request** from a branch, with the four checks green and the branch up to date with `main`. No approvals are required.
- Direct pushes, force-pushes and deleting `main` are not allowed.
- The repository admin can merge a PR **without** green CI (an explicit bypass, which is logged). Use it only in emergencies, such as CI broken by an external outage (wp-env downloads or GitHub Actions), never to skip a failing test.

To change the rules, edit the JSON in a PR and apply it with:

```bash
gh api repos/arinspunk/atproto-comments-plugin/rulesets           # gets the id
gh api -X PUT repos/arinspunk/atproto-comments-plugin/rulesets/<id> --input .github/rulesets/main.json
```

If you rename a workflow job, update the ruleset's required checks in the same PR.
